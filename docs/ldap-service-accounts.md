# Per-app LDAP service accounts

How to split `tofu/ldap-system-users` so each app (nextcloud, immich, ...) gets its own
bind account, its own Terraform state, and Flux-level ordering, instead of one module
owning everything.

## Principles

- The base module keeps owning the tree: OUs, password policies, the admin user and
  group, the `auth` bind user. It stays authoritative and rarely changes.
- Each app owns exactly one entry: `uid=<app>,ou=system`. Nothing else. This sidesteps
  the provider's co-management problem (see `docs/ldap-provider-rewrite.md`): two
  states never write the same entry.
- App bind credentials are generated by tofu (`random_password`) and delivered as a
  Kubernetes Secret via `writeOutputsToSecret`, in the app's own namespace, so the
  Deployment just mounts it. No human ever handles the password.
- Ordering is Flux-native: the Terraform CR gets a healthCheck, so the app's
  Kustomization is not Ready until the account exists; other apps can `dependsOn` it.

## Target layout

```
tofu/
  ldap/
    base/               # today's tofu/ldap-system-users, moved (state-safe: the
                        # Terraform CR keeps its name, only spec.path changes)
    service-account/    # small root module: vars app_name + admin bind, creates
                        # uid=<app>,ou=system with random password, outputs bind_dn
                        # + password
kubernetes/
  components/
    ldap-account/       # kustomize component, stamped like components/volsync
```

The component (implemented in `kubernetes/components/ldap-account/`, see its README)
mirrors the volsync design and rides the existing `${APP}` substitution:

- `secret.yaml`: an `${APP}-ldap-admin` Secret templated from a new
  `SECRET_LDAP_ADMIN_PASSWORD` in cluster-secrets (postBuild substitution already
  reaches every namespace), used as `varsFrom` for the provider bind.
- `terraform.yaml`: a Terraform CR named `${APP}-ldap`, `spec.path:
  ./tofu/ldap/service-account`, `vars: {app: ${APP}}`, `approvePlan: auto`,
  `writeOutputsToSecret: ${APP}-ldap-credentials`.

An app opts in with one component include plus a healthCheck:

```yaml
# apps/<ns>/nextcloud/app/kustomization.yaml
components:
  - ../../../../components/ldap-account

# apps/<ns>/nextcloud/ks.yaml
healthChecks:
  - apiVersion: infra.contrib.fluxcd.io/v1alpha2
    kind: Terraform
    name: nextcloud-ldap
    namespace: <ns>
dependsOn:
  - {name: openldap, namespace: identity}
  - {name: ldap-system-users, namespace: identity}  # base tree must exist
  - {name: tofu-controller, namespace: flux-system}
```

The app Deployment mounts `${APP}-ldap-credentials`; the pod cannot start before the
account exists, and the Kustomization reports not-Ready until the plan applied. That is
the "nextcloud is guaranteed a login account" property, with per-app blast radius: a
broken nextcloud plan cannot touch immich's account or the base tree.

## Prerequisites

1. tofu-controller 0.16.4 (Renovate PR #68) and the gRPC-hang follow-ups in
   `docs/tofu-controller-grpc-hang.md`; the controller must be reliable before
   multiplying Terraform CRs.
2. `runner.serviceAccount.allowedNamespaces` in the tofu-controller HelmRelease must
   list every namespace that runs a Terraform CR (plus its NetworkPolicy to reach
   source-controller).
3. `SECRET_LDAP_ADMIN_PASSWORD` added to cluster-secrets (sops; new key, added by the
   user). Done as of July 2026.

## Non-goals / gotchas

- App-specific groups (`cn=<app>-users`): create them in the base module, but leave
  membership to humans via canaille. Tofu asserting membership re-triggers the
  `data_json` fight documented in `docs/ldap-provider-rewrite.md`.
- Do not move Terraform CRs to flux-system for the gRPC workaround:
  `writeOutputsToSecret` lands in the CR's namespace, and the app must be able to
  mount the credentials Secret, so the CR belongs with the app.
- `userPassword` set through the provider is stored as given (no server-side hash on
  add); acceptable for machine accounts over LDAPS, same as `uid=auth` today.
